# ModNVote 2.2.0 — Linked Offices Manual Smoke Test

Release-candidate validation checklist for the **LINKED_OFFICES** ("Linked Offices
Election Model") lifecycle. Run this on a live Paper 1.21.x server with the shaded
plugin jar before tagging 2.2.0. Automated tests already regression-lock the
Bukkit-free service paths (`./gradlew clean test build`, 210 tests); this checklist
covers the in-server command/GUI surfaces those tests cannot drive.

- Server: Paper 1.21.x, ModNVote 2.2.0 RC jar installed, fresh `plugins/ModNVote`.
- Accounts: one admin (`modnvote.admin.*`, `modnvote.verify`), one or more voters.
- All commands below use the `/modnvote` base (`/poll` alias also works).
- Reference definition: `docs/examples/linked-offices-mayor-council.json`
  (Mayor = IRV, 1 seat; Council = APPROVAL_TOP_N, 4 seats, max 4 selections,
  `excludeWinnersFrom: [mayor]`).

Mark each item ✅ pass / ❌ fail and note observations.

---

## 1. Admin flow

| # | Step | Command / action | Expected |
|---|------|------------------|----------|
| 1 | Create | `/modnvote create linked_offices` | "Created DRAFT Linked Offices poll #N"; follow-up hint lists `config … set/import`, then `validate-definition`, `ready`, `open`. |
| 2 | Import definition | Copy the example JSON into `plugins/ModNVote/definitions/` and run `/modnvote config <N> import linked-offices-mayor-council.json` (or `config <N> set <json>`) | Definition stored; success message. |
| 3 | Edit-definition GUI | `/modnvote edit-definition <N>` | Linked Offices builder opens. Offices, Candidates and Dependencies screens navigable. Cycle method, adjust seats/max-selections, toggle abstain, add/remove an EXCLUDE_WINNERS dependency, then **Save**. Save message reads "Validate, mark the poll ready, then open it to let players vote." (no "not implemented" text). |
| 4 | Validate-definition | `/modnvote validate-definition <N>` | Reports VALID for the example. Intentionally break it (e.g. seats 0) and confirm it reports INVALID with specific issues; restore. |
| 5 | Show | `/modnvote show <N>` | Linked-offices view: poll type, status, "Definition: VALID", "Offices: 2 | Candidates: 7 | Dependencies: 1", and a brief per-office list (method/seats/candidate count). **No** ranking-rules block and **no** "No options configured." |
| 6 | Ready | `/modnvote ready <N>` | Poll → READY (re-validates definition). |
| 7 | Open | `/modnvote open <N>` | Poll → OPEN; open witness embed published if a webhook is configured. |

## 2. Voter flow

| # | Step | Command / action | Expected |
|---|------|------------------|----------|
| 1 | Vote GUI opens | `/modnvote vote <N>` (as a voter) | Linked Offices voting GUI opens for an OPEN poll. |
| 2 | Mayor (IRV) ranking | Rank Mayor candidates | Ordered ranking is captured; ordering is editable before submit. |
| 3 | Council approval / max selections | Select Council candidates | Approval selections capped at `maxSelections` (4); attempting a 5th is blocked. |
| 4 | Review screen | Advance to review | Review screen summarizes Mayor ranking and Council approvals accurately before submit. |
| 5 | Submit | Confirm submit | Submission succeeds; success message. |
| 6 | Proof phrase shown | (on submit) | The voter is shown their **proof phrase** at submission time — and only here. |
| 7 | Duplicate vote rejected | `/modnvote vote <N>` again as the same voter, attempt submit | Second submission is rejected; no second ballot recorded. |

Repeat steps 1–6 with several different voters to build a multi-ballot result.

## 3. Post-election

| # | Step | Command / action | Expected |
|---|------|------------------|----------|
| 1 | Close | `/modnvote close <N>` | Poll → CLOSED; closed-result witness embed published if a webhook is configured and `publication.publish_poll_closed: true`. |
| 2 | Result | `/modnvote result <N>` | Multi-contest result: Mayor winner + Council seats, counted-ballot total, completeness. EXCLUDE_WINNERS reflected (a Mayor winner is excluded from Council at counting time). |
| 3 | Publishresult | `/modnvote publishresult <N>` | Republishes the CLOSED result to configured webhooks (governed by `publish_poll_closed`). |
| 4 | Verify participation | `/modnvote verify participation <N>` (or `/modnvote verify <N>`) | Confirms the calling player's participation receipt without revealing vote content. |
| 5 | Verify ballot proof | `/modnvote verify ballot <N> <proofPhrase>` | A voter's own proof phrase verifies their anonymous ballot content; a wrong/garbage phrase fails cleanly. |
| 6 | Checkpoint | `/modnvote checkpoint <N>` | Publishes an integrity checkpoint (if a webhook is configured). |
| 7 | Witness publication | Inspect the configured Discord webhook channel | Open / closed-result / checkpoint embeds present and readable; long office fields truncate cleanly at the 1024-char limit. |

## 4. Privacy checks

Confirm across **result**, **witness/webhook**, **proof verification** and
**integrity** output that none of the following leak:

- [ ] No voter UUID, player name, IP hash, Floodgate ID, identity key,
      participation token hash, participation receipt, or anonymous ballot id
      appears in result, witness, or integrity output.
- [ ] The **proof phrase is shown only to the voter at submission** — it never
      appears in result, witness, integrity, or another player's view.
- [ ] `verify ballot` reveals only the anonymous ballot content tied to a
      proof phrase, with no link back to an identity.
- [ ] **EXCLUDE_WINNERS applies at count time, not vote time** — voters may
      still rank/approve a candidate who later wins another office; the
      exclusion is applied only when the result is computed.

| # | Step | Expected |

| 1 | YES_NO | `/modnvote create yes_no` → builder → ready → open → `/modnvote vote` → close → `/modnvote result`: unchanged single-contest behaviour. |
